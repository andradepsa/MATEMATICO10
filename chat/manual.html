Introduction

Chat K10 V46 is a decentralized communication platform that works without central servers. Unlike traditional chat apps (WhatsApp, Telegram, Discord), your messages never pass through a company database. You talk directly to other people (Peer-to-Peer) or through optional helper servers that you or your friends can run.

The entire application runs as a single HTML file — no installation, no account, no telemetry. Open it in any modern browser and you're ready to communicate privately.

Key Principles

🔒
End-to-end encryption (AES-256-GCM)Only the recipient can read your messages — not even a server owner.
🚫
No central databaseNobody stores your conversations. Data stays between peers only.
🌐
Runs in any browserNo installation required. Just open the HTML file and start chatting.
🔗
Share links, not heavy dataYouTube, radio, and most media are shared via URLs. Each user streams from the original source — the chat never carries video bytes.
⚠️
CRITICAL: The “Private” tab alone does NOT guarantee privacy.
When you send a message in the “Private” tab without encryption, the message travels in plain text. Due to network routing, it may be received and read by other users — including people connected to the same server or the same Hydra mesh.

✅ The only way to ensure that only you and the intended recipient can read the content is to activate bilateral E2EE (🔑) as described in the Encryption section below.

Four Network Topologies

The routing architecture of Chat K10 operates across four distinct topological flows. Understanding these communication paths explains how the network scales from two people to thousands.

TOPOLOGY 01
User ↔ User
Direct P2P channel. No servers, zero intermediary latency.
TOPOLOGY 02
User ↔ Server ↔ User
Star topology. A central server relays messages to a group.
TOPOLOGY 03
User ↔ Server ↔ Friendly Servers ↔ Users
Server Federation (Trees). Multiplies capacity immensely.
TOPOLOGY 04
General Mode (Hydra Mesh)
Controlled flooding. Everyone relays to everyone without bounds.
01

User ↔ User (Direct P2P)

Two browsers establish a direct WebRTC connection. No server is in the middle. The message travels directly from sender to recipient over the shortest possible network path.

✅ Best forPrivate one-on-one conversations, voice/video calls, file transfers.
02

User ↔ Server ↔ User (Central Relay)

Everyone connects to one central server (ID ending with -CENTRAL). The server rebroadcasts messages to all connected users.

✅ Best forStable group chats, users behind strict firewalls or symmetric NATs.
03

User ↔ Server ↔ Friendly Servers ↔ Users (Federation)

A “Tree” topology. Servers link together; messages propagate across all federated servers.

✅ Best forMassive audiences crossing the 200-user limit.
04

General Mode (Hydra Mesh / Flooding)

No central server. Messages hop from user to user (up to 15 hops TTL). Every node uses an LRU cache of 10,000 message IDs to drop duplicates.

✅ Best forCensorship‑resistant broadcasting, automatic overflow when servers are full.
⚠️
In General Mode, every message is broadcast to the entire mesh. If you need private conversation with two people only, do not use General Mode – select the contact in the Private tab and activate E2EE (🔑).

Server Features

Open ServidorChatK10.html to become a server owner. Your computer will relay messages for other users. The server interface provides full control and real-time statistics.

🤝
Friendly Servers — Server Federation

A server can add another server (ID ending with -CENTRAL) as a contact. Once connected, the two servers form a federation. When User A sends a message: Server A broadcasts to its own users → forwards to every federated server → each federated server broadcasts to its users. The same TTL and anti‑loop cache applies. Each server handles up to 200 users — federation allows thousands across multiple servers.

📺
YouTube Live Chat Broadcasting

The server can mirror a YouTube Live chat to all connected users. They see a second tab — Chat YouTube — with the live comments embedded. Start: click "Start YT Chat" and paste the YouTube Live URL. Individual clients can also start/stop YouTube Live Chat independently (Tools → Start YouTube Chat).

🐉
Auto-Hydra Mode — Self-Scaling

When the server reaches 150 connected users, it automatically switches to Hydra mode: it sends a list of known peers to everyone, then disconnects. All users migrate to the General Web (P2P mesh) — the chat never stops. This is how the network scales infinitely without crashing the server.

📊
Server Statistics (Real-Time)

Live dashboard shows: messages received / distributed · active connections · estimated Hydra Web size (P2P node count) · audit log with all connection events.

📜

Audit Log & Network Health

The Audit Log (📜 Audit Log) is the "Pulse" of the Chat K10 network. It ensures complete transparency by logging real-time connectivity events, errors, and automated maintenance actions across the entire decentralized structure.

🔍 Automated Monitoring

Both Client and Server instances maintain their own detailed Audit Logs to detect "Ghost Connections" and verify synchronization. Every entry includes a precision timestamp and is color‑coded by severity category.

✅ OKSuccessful handshakes, peer connections established.ℹ️ INFOHydra network structural changes (group split/merge) or auto‑reconnection logs.⚠️ WARNGhost connection detected by GC, peer disconnected.❌ ERRORPeer ID already in use, remote peer not found.
GC

The "Ghost Connection" Garbage Collector

Chat K10 runs an active Garbage Collector (GC) every 5 seconds to ensure network stability. It monitors the connectionState of every remote peer; if a peer is failed, closed, or disconnected, the GC force‑closes the socket and purges UI references.

Encryption (E2EE) — The Only Real Privacy

🚨
READ THIS FIRST: The "Private" tab only organises the interface – it does NOT encrypt your messages. Without encryption, your messages travel in plain text and can be read by other users or server operators if routing goes wrong.

You must activate bilateral E2EE (🔑) to ensure that only the intended recipient can read the content. With encryption active (🔒 icon next to the contact), even if a message is misrouted, nobody else can decrypt it.

Step-by-Step to Activate Encryption

1
Click the 🔑 button in the message input bar
A modal window opens listing your online contacts.
2
Select the contact who is online and connected
Only currently online contacts appear as selectable.
3
Click "Send Secret Now"
Your browser generates a unique cryptographic secret and sends it directly via P2P — the server never sees it.
4
The other person must do the same for you
⚠️ Critical: encryption is bidirectional. They must also click the button and send their secret to you. Sending only yours is not enough.
5
Look for the lock icon — you're fully encrypted
Once both sides have exchanged secrets, a 🔒 appears next to the contact's name. All subsequent messages are E2EE.

Encryption Indicators

🔒
Full E2EE ActiveBoth sides exchanged secrets. All messages encrypted in both directions.
📤
Sending EncryptedYou sent your secret, but the other side hasn't replied yet. Your outbound messages are encrypted; inbound are not.
📥
Receiving EncryptedYou can read their encrypted messages, but you haven't sent your secret yet.
🔐
Group EncryptionGroup E2EE active on a server. Messages pass through fully encrypted — the server sees only ciphertext.
✅
With E2EE active (🔒), your conversation becomes truly private. Even if the network misroutes a packet, only you and the recipient hold the keys to decrypt it. This is the only way to prevent message "leaks" to other users.

Group Encryption on Servers

If connected to a -CENTRAL server, you can activate group encryption. Prerequisite: you must have exchanged individual secrets with every participant first. Click the encryption button next to the server in the conversations list. A group secret is generated and sent to all contacts who already have E2EE with you. From then on, all messages through that server are encrypted — the server sees only gibberish. Users without the group secret see blank messages.

⚠️
New users joining later do not automatically receive the group secret. An existing participant must manually share it with them out‑of‑band.

Invite Links & Sharing

Peer IDs

Every user and every server has a unique Peer ID. Client IDs are 9 random characters (e.g., A3BX7KQ2P). Server IDs must end with -CENTRAL (e.g., MyServer-CENTRAL). Your ID appears in the blue bar — click Copy to share it.

Invite Links (Client Only)

Only the Chat K10 client (not the server) can generate invite links. Click Generate Invite Link. A complete URL is created containing your ID and the IDs of the first 15 users from your active connections list. When someone opens that link, they automatically connect to all listed IDs.

Groups in V46 — Logical Rooms & Binary Protocol

01

Fixed Peer ID vs. Logical Group ID

🔐 Peer ID (permanent)Random 9‑character string stored in localStorage. It never changes, ensuring your private conversations, contacts and files remain attached to you.🧩 Logical ID (volatile)Built as K10 + GID (4 chars) + suffix (2 chars). Changes when you move between rooms or when the group reorganises itself.
02

The Fixed Suffix List — No More Name Spam

Every copy of Chat K10 V46 contains an identical, hard‑coded list of 1,800 suffixes (AA … dB). Because all clients share the same list, the server never sends the full set of names. Instead, it sends only the total number of people in the group (count). This reduces group‑update bandwidth by up to 83%.

03

Binary Protocol — 7‑Byte Messages

All group join/leave events are transmitted as ultra‑lightweight binary packets (7 bytes). No JSON, no human‑readable names — just raw bytes. This includes JOIN_UPDATE (when someone joins) and PEX_UPDATE / SWAP-ON-LEAVE (when someone leaves).

🌿

V27 Homeostatic Protocol (Mitosis · Tutelage · Compensation · Fusion)

Chat K10 V27 extends the group system with a server‑driven homeostasis layer. The central server automatically monitors group sizes and applies corrective actions to keep the network balanced and scalable beyond 1800 users.

K10_SPLIT_THRESHOLD = 1800 // triggers mitosis
K10_TUTOR_TARGET = 1700 // child group considered adult
K10_MERGE_THRESHOLD = 1700 // fusion if parent+child ≤ this
K10_COMPENSATE_DELTA = 100 // users transferred per cycle

Handlers implemented: group-split, group-tutor-status, group-alert, group-compensate, group-merge, group-orphan-rescue. Peer ID never changes; only myGroupIdRef is updated.

⏱️
Debounce (5 minutes) prevents “frenetic merging” when sizes oscillate near the threshold.
🧠

System Architecture & P2P Physics

Messaging in the General Web operates through a bidirectional chain: Parent ↔ Child ↔ Grandchild. To prevent infinite broadcast storms, every message has a TTL (Time‑To‑Live) (max 15 hops) and every node maintains an LRU cache of 10,000 message IDs to drop duplicates.

01

Organic Propagation: The Reciprocal Flow

The Hydra mesh ensures no echo loops via the "I've Seen It" log (LRU cache) and the TTL counter. Every message dies after 15 hops.

02

The Bouncer: Auto‑Hydra at 200 Users

When a server reaches its physical limit (150-200 concurrent WebSockets), it stops acting as a central relay and becomes a "tracker". It hands over a Peer Exchange (PEX) list and disconnects, pushing users onto the infinite Mesh.

03

Friendly Servers (Federated Trees)

Servers can federate by inserting another server's -CENTRAL ID. An invisible WebRTC channel links Server A and B, allowing thousands of users to behave as if they share one room.

FAQ & Troubleshooting

“I’m in the Private tab, but other users receive my messages!” —
Cause: You haven't activated E2EE encryption. Without encryption (🔒), messages travel in plain text and network routing bugs can cause them to be delivered to unintended recipients – especially if you are connected to a server or the Hydra mesh.

Solution: Activate bilateral encryption (🔑) with your intended contact. Once both sides have exchanged secrets (🔒 appears), the messages are encrypted end‑to‑end. Even if a packet is misrouted, no one else can decrypt it. This is the only way to guarantee that only the two of you read the conversation.
“Encryption doesn't work” —
Both sides must exchange secrets. Just sending your secret is not enough – the other person must also click the 🔑 button and send their secret to you. Check the indicator: 🔒 means fully active E2EE.
“The server is full / I got a migration message” —
The server reached its 150‑user Auto‑Hydra threshold. You were automatically moved to the General Web — this is normal and good; the network is scaling.
“Quiz Bot questions appear in the wrong language” —
Change your language in the header dropdown. The next questions will be auto‑translated via Google Translate.
“What happens if I stop the Quiz Bot?” —
If you click "Stop Bot", the bot automatically transfers to the connected server (if any). The server continues sending questions from exactly where you left off. If no server is connected, the bot stops completely.
“My video call is laggy” —
Video calls depend on your upload speed. Switch to voice‑only for a much lighter load. Use direct P2P mode for best performance.
“I can't send files larger than 5 MB” —
For larger files, use the Torrent Manager in the Tools menu — it supports files up to 500 MB via WebTorrent (only the magnet link travels through the chat).
“What is the difference between a Peer ID and an Invite Link?” —
Peer ID: A 9‑character code that identifies you. Invite Link: A full URL generated only by the client that auto‑connects to multiple peers.
“How does the General Web have no user limit?” —
There is no central server. Each user connects to up to 15 others (50 in SuperNode mode). Messages hop up to 15 times (TTL). The network grows organically — more users make it stronger, not weaker.
