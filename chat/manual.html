Introduction

Chat K10 V27 is a decentralized communication platform that works without central databases. Unlike traditional chat apps, your messages never pass through a company-controlled server. You talk directly to other people (Peer-to-Peer) or through optional helper servers that you or your friends can run.

The entire application runs as a single HTML file — no installation, no account, no telemetry. Open it in any modern browser and you're ready to communicate privately.

Four Network Topologies

The routing architecture of Chat K10 operates across four distinct topological flows. Understanding these communication paths explains how the network scales from two people to thousands.

TOPOLOGY 01
User ↔ User
Direct P2P channel. No servers, zero intermediary latency.
TOPOLOGY 02
User ↔ Server ↔ User
Star topology. A central server relays messages to a group.
TOPOLOGY 03
User ↔ Server ↔ Friendly Servers ↔ Users
Server Federation (Trees). Multiplies capacity immensely.
TOPOLOGY 04
General Mode (Hydra Mesh)
Controlled flooding. Everyone relays to everyone without bounds.

Groups in V27 — Homeostatic Protocol

Chat K10 V27 introduces a self‑healing, homeostatic group system. Groups no longer just exist — they actively split when full, tutor newborn groups, compensate size imbalances, and merge when they become too small. This ensures that the entire network remains balanced, responsive, and scalable up to thousands of participants without manual intervention.

01

Fixed Peer ID vs. Logical Group ID

Every user has two distinct identities:

🔐 Peer ID (permanent)Random 9‑character string (e.g. K29XMQBR7) stored in your browser’s localStorage. It never changes — even when you move between groups or when a group splits/merges. Your private conversations, contacts and files remain attached to this permanent ID. 🧩 Logical ID (volatile)A virtual address built as K10 + GID (4 chars) + suffix (2 chars). Example: K10AAAAAA. This ID changes when you move between rooms or when the group reorganises itself. The GID (Group ID) is the only thing that may change; the Peer ID stays untouched.
💡
The Peer ID is what you use for direct P2P calls and file transfers. The Logical ID is only used to position you inside a group. V27 guarantee: no handler ever modifies peerIdRef.current.
02

The Fixed Suffix List — No Name Spam

Every copy of Chat K10 V27 contains an identical, hard‑coded list of 1,800 suffixes (K10_POSITION_LIST). Because all clients share the same list, the server never sends the full set of names. Instead, it sends only the total number of people in the group (count). Each client then calculates which suffixes to connect to.

“If the group has 10 members, I will connect to suffixes at positions 0 through 9 of my internal list.”

This optimisation reduces group‑update bandwidth by up to 83% compared to older versions.

03

Binary Protocol — 7‑Byte Messages

All group join/leave events are transmitted as ultra‑lightweight binary packets. No JSON, no human‑readable names — just raw bytes.

📥 JOIN_UPDATEServer broadcasts a 7‑byte packet when a user joins. All clients open a direct WebRTC connection to the new logical ID. 📤 SWAP-ON-LEAVE + PEX_UPDATEWhen someone leaves, the last member moves to the vacant slot. Only the moved user receives a private position-update; the group only sees the new count.
🌿

Homeostatic Protocol — Mitosis · Tutelage · Compensation · Fusion

V27 adds a server‑driven homeostasis layer that constantly monitors group sizes and applies corrective actions. The central server (any -CENTRAL node) evaluates these conditions every few seconds.

K10_SPLIT_THRESHOLD1800 — when a group reaches this size, mitosis splits it. K10_TRANSFER_SIZE180 — the 10% most recent users move to the child group. K10_TUTOR_TARGET1700 — child group is considered adult and tutelage ends. K10_CRITICAL_LOW1400 — triggers compensation (transfer users from the larger sibling). K10_MERGE_THRESHOLD1700 — if parent + child ≤ 1700 for 5 minutes, they fuse.
🧠
All these operations are transparent to the user. You never lose connectivity, and your Peer ID remains unchanged — only your group (GID) may be updated.
04

Mitosis — When a Group Becomes Full

When a group reaches 1800 members (the hard limit), the server automatically triggers a split:

  • The server selects the 180 most recent users (lowest session time) and moves them to a newly created child group.
  • The original group (parent) keeps 1620 users.
  • The child group starts with 181 users (180 transferred + the new user that caused the split).
  • All clients receive a group-split message. Those transferred see their GID change automatically; others only update their directory.
  • Peer IDs never change — only the group affiliation (GID) changes.
⚠️
After a split, the child group enters tutelage — the parent server will route most new users to the child until it reaches a healthy size.
05

Tutelage & Weighted Routing

Newborn groups are fragile. The server acts as a tutor, directing traffic to the child group until it matures.

📊 Weighted routing table • Child < 500 users → 95% of new users go to child.
• 500–999 → 80% to child.
• 1000–1499 → 60% to child.
• 1500–1699 → 30% to child.
• ≥ 1700 → 0% (tutelage ends). 📡 group-tutor-statusThe server broadcasts the current tutelage state. Clients store it locally for routing hints (used when they act as relays). 🎓 End of tutelageWhen child reaches 1700, the server sends active: false and stops preferential routing.
06

Compensation & Alerts — Fixing Imbalances

If a group falls below 1400 users (critical low), the server activates compensation:

  • A group-alert (level "red") is sent to all clients.
  • The larger sibling group (parent or child) donates 100 users (K10_COMPENSATE_DELTA) to the weak group.
  • Both groups end up with approximately (total / 2) users.
  • If a group is between 1400 and 1600, a yellow alert is issued — the group stops accepting new users until it recovers.
⚖️
Compensation is mutual. After a compensation cycle, the donor and receiver sizes are equalized, preventing cascading failures.
07

Fusion — Reverse Entropy

When both parent and child groups become small, the server merges them back into a single healthy group.

🔍 ConditionparentSize + childSize ≤ 1700 for at least 5 minutes (K10_MERGE_DEBOUNCE_MS). 🕹️ Debounce mechanismThe server monitors group sizes via group-size-report. If the sum stays ≤ 1700 for 5 minutes without oscillation, it sends group-merge. 📦 Survivor & dissolvedThe group with the larger size survives; the other is dissolved. All members of the dissolved group are migrated to the survivor. 📐 Post‑merge marginThe resulting group has ≤ 1700 users, leaving a 100‑user buffer before the yellow alert (1600).
⏱️
The 5‑minute debounce prevents “frenetic merging” when sizes oscillate around the threshold.
08

Orphan Rescue — Server Failure Tolerance

If the server that hosts a child group goes offline (no heartbeat for 30 seconds), the parent server detects the absence and sends a group-orphan-rescue message.

  • The orphaned group’s users are reabsorbed into the parent group.
  • The orphan GID is removed from the global directory.
  • All affected clients automatically update their myGroupIdRef to the rescuer group.
  • Peer ID never changes — only the group affiliation.
🛡️
This ensures no user is left stranded if a group’s server crashes.

Security Rules — Who Can Modify the Group?

🏛️
Only the central server can send homeostatic commandsMessages like group-split, group-compensate, group-merge are ignored unless they come from a valid -CENTRAL server. This prevents malicious peers from splitting or merging groups arbitrarily.
🗑️
Deduplication via msgIdEvery operation includes a unique msgId. Clients store the last 256 IDs in a Set and discard duplicates, preventing replay attacks.
🔄
Peer ID is immutableNone of the V27 handlers modify peerIdRef.current. Only myGroupIdRef.current (the GID) can change, preserving your permanent identity.

How to Create or Join a Group (User Guide)

1
Open the Group Panel
Click the 👥 Groups button next to the server list or use Tools → Groups.
2
Create a New Group
Click Create Group and choose a 4‑character GID (e.g. AAAA, MUSIC, GAME). The server assigns you the first suffix (position 0).
3
Join an Existing Group
Ask any member for the GID. Type it into the Join Group field and press Join. The server assigns the next free suffix.
4
Automatic homeostatic actions
If the group becomes full (1800), you might be moved to a new child group during mitosis. Your Peer ID stays the same; you only see the GID change in the interface. No action is required from you.
5
Leave a Group
Click 🚪 Leave Group. The server triggers SWAP-ON-LEAVE to fill the empty slot.
📡
Note: Groups require a central server (-CENTRAL) to coordinate the homeostatic protocol. In pure P2P General Web mode, groups are not available – use direct contacts or the Hydra mesh instead.

FAQ & Troubleshooting

"What happens if my group splits?" —
If you are among the 10% most recent users, you will be moved to a new child group automatically. Your Peer ID stays the same; you just see a different GID. Your chat history and contacts remain intact.
"Can I prevent being moved during a split?" —
No, the split is managed by the server to balance load. The process is seamless — you don’t lose messages or connections.
"Do I need to update my server to V27?" —
Yes. The server must implement the seven new handlers (group-split, group-tutor-status, etc.) for homeostasis to work. The client V27 is backward‑compatible with older servers (no split/merge will happen).
