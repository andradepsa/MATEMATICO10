Introduction

Chat K10 V18 is a decentralized communication platform that works without central servers. Unlike traditional chat apps (WhatsApp, Telegram, Discord), your messages never pass through a company database. You talk directly to other people (Peer-to-Peer) or through optional helper servers that you or your friends can run.

The entire application runs as a single HTML file — no installation, no account, no telemetry. Open it in any modern browser and you're ready to communicate privately.

Key Principles

🚫
No central databaseNobody stores your conversations. Data stays between peers only.
🔐
End-to-end encryption (AES-256-GCM)Only the recipient can read your messages — not even a server owner.
🌐
Runs in any browserNo installation required. Just open the HTML file and start chatting.
💾
Works offline / on a USB stickPerfect for emergencies, restricted networks, LAN parties, or air-gapped environments.
🔗
Share links, not heavy dataYouTube, radio, and most media are shared via URLs. Each user streams from the original source — the chat never carries video bytes.
ℹ️
Who is Chat K10 for? Friends who want private, uncensored conversations · Communities that don't trust corporate apps · Educational groups (Quiz Bot, Whiteboard) · Events, LAN parties, or situations with limited internet access.

Four Network Topologies

The routing architecture of Chat K10 operates across four distinct topological flows. Understanding these communication paths explains how the network scales from two people to thousands.

TOPOLOGY 01
User ↔ User
Direct P2P channel. No servers, zero intermediary latency.
TOPOLOGY 02
User ↔ Server ↔ User
Star topology. A central server relays messages to a group.
TOPOLOGY 03
User ↔ Server ↔ Friendly Servers ↔ Users
Server Federation (Trees). Multiplies capacity immensely.
TOPOLOGY 04
General Mode (Hydra Mesh)
Controlled flooding. Everyone relays to everyone without bounds.
01

User ↔ User (Direct P2P)

Two browsers establish a direct WebRTC connection. No server is in the middle at any point. The message travels directly from sender to recipient over the shortest possible network path.

✅ Best forPrivate one-on-one conversations, heavy WebRTC file transfers, or Voice/Video calls. ⚡ AdvantageFastest and most private — works completely offline (LAN/USB) and survives if all servers die. ▶ How it worksAdd the other person's Peer ID as a contact, click their name, and send.
02

User ↔ Server ↔ User (Central Relay)

A "Star" topology. Everyone connects to one central server (ID ending with -CENTRAL). When a user sends a message, it goes to the server, and the server immediately rebroadcasts it to all other connected users.

✅ Best forStable group chats and users trapped behind strict corporate firewalls or symmetric NATs. ⚡ AdvantageVery stable coordination (up to 200 users per node). Perfect for classrooms or managed events. ▶ How it worksOpen ServidorChatK10.html, then have users add that server's ID to their lists.
03

User ↔ Server ↔ Friendly Servers ↔ Users (Federation)

A "Tree" topology. Server limits are easily bypassed by linking servers together. When User A sends a message to Server A: Server A broadcasts to its local users, AND forwards it to Server B (a Friendly Server). Server B then broadcasts the message to all of its local users.

✅ Best forMassive audiences crossing the 200-user limit, like large global announcements or mega-events. ⚡ AdvantageAllows thousands of users across multiple servers. If one server goes offline, local segments survive. ▶ How it worksIn the Server UI, the owner adds another server's -CENTRAL ID to form the Federation Bridge.
04

General Mode (Hydra Mesh / Flooding)

An unstructured, decentralized "Mesh" topology. No central server is required. When a message is sent, it is broadcast to all of your immediate contacts. Those contacts forward it to their contacts, and so on. To prevent infinite loops, every message carries a TTL (Time To Live) counter, and every node uses a high-speed LRU Hash Cache to silently drop duplicate IDs.

✅ Best forCensorship-resistant anonymous broadcasting and automatic spill-over when servers get full. ⚡ AdvantageInfinite scalability. The more peers that join, the stronger the network paths become. ▶ How it worksDeselect all contacts in the UI. The header shows "GENERAL MODE ACTIVATED". Type and send.

Server Features

Open ServidorChatK10.html to become a server owner. Your computer will relay messages for other users. The server interface provides full control and real-time statistics.

🤝
Friendly Servers — Server Federation

A server can add another server (ID ending with -CENTRAL) as a contact. Once connected, the two servers form a federation. When User A sends a message: (1) Server A broadcasts to its own users → (2) Server A forwards to every federated server → (3) each federated server broadcasts to its users. The same TTL and anti-loop cache applies. Each server handles up to 200 users — federation allows thousands across multiple servers. Resilience: if one server goes down, others continue. Users never need to know about federation; it's completely transparent.

▶
In the server interface, type the other server's ID (must end with -CENTRAL) in the "Connect to another Server" field and click Connect.
📺
YouTube Live Chat Broadcasting

The server can mirror a YouTube Live chat to all connected users. They see a second tab — Chat YouTube — with the live comments embedded. Start: click "Start YT Chat" and paste the YouTube Live URL. Stop: click "Stop YT Chat".

Individual clients can also start and stop YouTube Live Chat independently (via Tools → Start YouTube Chat), sending the live comment tab to their contacts without needing the server.

🐉
Auto-Hydra Mode — Self-Scaling

When the server reaches 150 connected users, it automatically switches to Hydra mode: it sends a list of known peers to everyone, then disconnects. All users migrate to the General Web (P2P mesh) — the chat never stops. The hard cap is 200 connections; beyond that, new connections are rejected or migrated. This is how the network scales infinitely without crashing the server.

Audit Log & Network Health

The Audit Log (📜 Audit Log) is the "Pulse" of the Chat K10 network. It ensures complete transparency by logging real-time connectivity events, errors, and automated maintenance actions across the entire decentralized structure.

🔍 Automated Monitoring

Both Client and Server instances maintain their own detailed Audit Logs to detect "Ghost Connections" and verify synchronization. Every entry includes a precision timestamp and is color-coded by severity category.

✅ OKSuccessful handshakes, peer connections established, or server becoming active. ℹ️ INFOHydra network structural changes (group split/merge) or auto-reconnection logs. ⚠️ WARNGhost connection detected by GC, peer disconnected, or non-fatal WebRTC signaling delays. ❌ ERRORPeer ID already in use, remote peer not found, or total loss of connectivity to signaling broker.
GC

The "Ghost Connection" Garbage Collector

In decentralized mesh networks like Hydra, WebRTC sockets can occasionally fail silently (entering a "phantom" or "zombie" state). Chat K10 runs an active Garbage Collector (GC) every 5 seconds to ensure network stability.

ScanningMonitors the connectionState of every remote peer in the activeConnections pool. CleansingIf a peer is failed, closed, or disconnected, the GC force-closes the socket and purges UI references. DeduplicationEnsures the PeerGroupMap is cleaned up to maintain accurate server and Hydra statistics. Audit EntryLogs [GhostGC] Phantom peer detected and removed to explain why a node suddenly disappeared.
⏰

Network Sync & Health Schedule

To ensure Chat K10 remains fast and doesn't slow down your computer, it doesn't process everything at once. It follows a strict schedule of automated cleaning and updates:

Every 30 secPEX & Presence: Each user notifies friends they are online and "refers" other known contacts. This is how the contact list grows automatically without a central server. Every 60 secNetwork Census (Directory): Leaders and servers count the group members and propagate this figure so everyone can see the real size of the Hydra network. After 90 secSilence Eviction: If someone stops sending the "I'm alive" signal for more than 90 seconds, the system assumes they've disconnected and removes them from the list. Always (3-5s)Technical Cleanup (Ghost GC): The network engine monitors virtual connections. If an immediate technical error is detected, it removes the "ghost" from the screen in seconds, without waiting for the 90-second silence period. ImmediateHandshake: The moment you connect to someone new, the contact exchange happens within the first 5 seconds to ensure you don't remain isolated.

📚 Glossary: Understanding Technical Terms

If you're not a programmer, here's a simple explanation of what these terms mean in practice:

🗣️
PEX (Peer Exchange) — "Word of Mouth"It's like being introduced to a new friend at a party. In the chat, your computer tells others who it knows so everyone stays connected without needing a "boss" (server) in the middle.
💓
Heartbeat — "The Vital Pulse"A small automatic signal sent silently every 30 seconds. It simply says: "Hey, I'm still here!". If the heart stops beating, the chat knows you've left.
👻
Ghost Connection — "Phantom Connection"Sometimes a signal drops, but the chat still shows the person there (like a ghost). Our janitor (GC) notices the "body" is present but the "soul" (signal) is gone, and clears the screen so you don't send messages into a vacuum.
🦘
TTL (Time To Live) — "Hop Limit"Since the Hydra network is a web, messages hop from person to person. To prevent messages from looping forever, they have a "ticket" valid for 15 hops. Once the ticket is used up, the message stops traveling.
🐉
Hydra Mesh — "The Spider Web"Unlike WhatsApp (where everything goes to a central company), here the network is like a web. If the center of the web tears, the outer threads keep holding everything together. It's a network with no owner and is impossible to shut down.
🌐
WebRTC — "Direct Cable"Technology that allows two browsers to talk directly, as if there were a cable connected between the two computers, with nothing in between.
🔒
E2EE (End-to-End Encryption) — "The Locked Box"Imagine putting your message in a steel box and locking it with a padlock. Only you and the recipient have the key. Even if someone (like a server owner) intercepts the box, they can't see what's inside.
🏰
Federation — "Alliance of Cities"When two or more servers decide to work together. It's like two independent cities building a bridge so their citizens can visit and converse freely.
🧱
Symmetric NAT / Firewall — "The Gated Community Wall"Some internet networks (like companies or universities) are like gated communities with very strict security that won't let strangers in. This can make direct connections between users difficult.
💻

▶️ YouTube — All Possibilities

YouTube is deeply integrated into Chat K10. There are five distinct ways to use it, all available to any user — no special permissions required.

💡
The chat never carries video bytes. Only the video ID (or playlist ID) and a sync timestamp travel through the P2P network. Each user's browser streams the content directly from YouTube's servers, keeping traffic minimal and copyright compliance intact.

1 · YouTube Radio — Any User Can Broadcast Any Live, Video or Playlist

Any connected user can act as a broadcaster at any time. This includes YouTube live streams — not just recorded videos. To start:

  1. Click Tools → YouTube Radio (or the YouTube Radio button).
  2. Paste any YouTube URL: a normal video, a live stream (youtube.com/live/… or watch?v=…), or a playlist (list=…).

  4. All recipients automatically receive a radio-youtube-start message and a floating player opens on their screen, tuned to the same point in the stream.

When the broadcaster stops the transmission (Stop YouTube Radio), all players close automatically on every connected client.

2 · Synced Playback (startTime)

For recorded videos and playlists, the sender calculates a startTime a few seconds in the future and embeds it in the broadcast message. When that moment arrives every recipient starts playing simultaneously — eliminating the "who's ahead?" problem in watch parties. For live streams the player simply joins the live edge, so everyone watches the same live moment.

3 · Floating Player Controls

The YouTube player appears in a draggable, resizable floating window. Options available during playback:

  • Show / Hide Video — toggle to listen as audio-only (background music mode).

  • Individual volume control inside the YouTube iframe.

4 · Quick-Grid of Favourite Links (1–103)

The YouTube Radio panel shows a numbered grid from 1 to 103. Each slot can store a custom YouTube URL (video, live, or playlist):

  • Left-click a number to immediately broadcast that link to the room.
  • Right-click a number to edit / replace its saved URL.

Numbers with a saved link appear highlighted in blue; empty slots appear white. The grid makes switching between DJ sets, live channels, or playlists instant — no copy-paste required.

5 · YouTube Live Chat (Comments Tab)

Separate from the video stream, any user (or the server) can relay the comment section of a YouTube Live to everyone in the room. This opens a second tab — Chat YouTube — displaying the live comments via YouTube's official embed (youtube.com/live_chat?v=…). Two ways to start it:

  • Server: Click Start YT Chat in the server interface → paste the live URL → all connected clients receive the comments tab. Stop with Stop YT Chat.
  • Any client: Click Tools → Start YouTube Chat → paste the live URL → the comments tab propagates to all P2P contacts. Stop with Stop YouTube Chat.

The comments tab and the video stream (YouTube Radio) are independent — you can run both at the same time for a full watch-party experience: video playing in the floating window, live comments visible in the side tab.

Encryption (E2EE)

Chat K10 uses AES-256-GCM encryption with PBKDF2 key derivation. Nobody except you and the recipient can read your messages — not even the server owner. Encryption must be activated manually and requires both parties to exchange secrets.

Step-by-Step to Activate Encryption

1
Click the 🔑 button in the message input bar
A modal window opens listing your online contacts.
2
Select the contact who is online and connected
Only currently online contacts appear as selectable.
3
Click "Send Secret Now"
Your browser generates a unique cryptographic secret and sends it directly via P2P — the server never sees it.
4
The other person must do the same for you
⚠️ Critical: encryption is bidirectional. They must also click the button and send their secret to you. Sending only yours is not enough.
5
Look for the lock icon — you're fully encrypted
Once both sides have exchanged secrets, a 🔒 appears next to the contact's name. All subsequent messages are E2EE.

Encryption Indicators

🔒
Full E2EE ActiveBoth sides exchanged secrets. All messages encrypted in both directions.
📤
Sending EncryptedYou sent your secret, but the other side hasn't replied yet. Your outbound messages are encrypted; inbound are not.
📥
Receiving EncryptedYou can read their encrypted messages, but you haven't sent your secret yet.
🔐
Group EncryptionGroup E2EE active on a server. Messages pass through fully encrypted — the server sees only ciphertext.

Group Encryption on Servers

If connected to a -CENTRAL server, you can activate group encryption. Prerequisite: you must have exchanged individual secrets with every participant first. Click the encryption button next to the server in the conversations list. A group secret is generated and sent to all contacts who already have E2EE with you. From then on, all messages through that server are encrypted — the server sees only gibberish. Users without the group secret see blank messages.

⚠️
New users joining later do not automatically receive the group secret. An existing participant must manually share it with them out-of-band.

Groups in V26 — Logical Rooms & Binary Protocol

Chat K10 V26 introduces a completely redesigned group system that eliminates bandwidth waste and scales to thousands of participants without flooding the network with long lists of names. Groups are now logical rooms where every member is identified by a compact, position‑based address.

01

Fixed Peer ID vs. Logical Group ID

Every user has two distinct identities:

🔐 Peer ID (permanent)Random 9‑character string (e.g. K29XMQBR7) stored in your browser’s localStorage. It never changes, ensuring your private conversations, contacts and files remain attached to you across sessions. 🧩 Logical ID (volatile)A virtual address built as K10 + GID (4 chars) + suffix (2 chars). Example: K10AAAAAA. This ID changes when you move between rooms or when the group reorganises itself.
💡
The Peer ID is what you use for direct P2P calls and file transfers. The Logical ID is only used to position you inside a group.
02

The Fixed Suffix List — No More Name Spam

Every copy of Chat K10 V26 contains an identical, hard‑coded list of 1,800 suffixes (K10_POSITION_LIST). These range from AA, AB, AC … up to ZZ (plus extra combinations).

Because all clients share the same list, the server never sends the full set of names. Instead, it sends only the total number of people in the group (count). Each client then calculates:

“If the group has 10 members, I will connect to suffixes at positions 0 through 9 of my internal list.”

This single optimisation reduces group‑update bandwidth by up to 83% compared to older versions.

03

Binary Protocol — 7‑Byte Messages

All group join/leave events are transmitted as ultra‑lightweight binary packets. No JSON, no human‑readable names — just raw bytes.

📥 When someone JOINS (JOIN_UPDATE)

The central server sends you a peer‑list message containing: your gid, your assigned suffix (position), and the new count. For every other existing member, the server broadcasts a binary JOIN_UPDATE packet.

  • Upon receiving this packet, each client sees that count increased.
  • They immediately attempt to open a direct P2P WebRTC connection to the newly calculated Logical ID.

📤 When someone LEAVES (SWAP-ON-LEAVE + PEX_UPDATE)

The system never leaves “holes”. If the member at position 3 leaves a group of 10:

  1. The user who was in the last position (position 9) is moved to position 3.
  2. The server sends a position-update only to that moved user, informing them of their new suffix.
  3. The server then broadcasts a binary PEX_UPDATE to the whole network, stating that the group now has count = 9.
⚡
All these messages are exactly 7 bytes long — incredibly efficient even for very large groups or spotty connections.
🔒

Security Rules — Who Can Modify the Group?

To prevent malicious peers from injecting fake members or crashing the group, V26 enforces strict rules:

🏛️
Only the central server can increase countJOIN_UPDATE messages from ordinary peers are ignored. This prevents a single bad actor from claiming “100 people joined” and overwhelming everyone.
🗑️
Peers can only report departuresWhen a client detects a silent disconnect (e.g. no heartbeat for 90 seconds), it may broadcast a PEX_UPDATE to decrease the counter. The server accepts these but never allows an increase from a non‑server source.
🔄
Position updates are unicastThe moved user receives a private position-update; the rest of the group only sees the new count. No one else knows exactly who moved, preserving privacy.

V27 Addition — Homeostatic Protocol (Mitosis · Tutelage · Compensation · Fusion)

Chat K10 V27 extends the group system with a server‑driven homeostasis layer. The central server automatically monitors group sizes and applies corrective actions to keep the network balanced, responsive, and scalable beyond 1800 users. This section documents the protocol for server implementers.

📐

Homeostatic Constants

const K10_SPLIT_THRESHOLD = 1800; // dispara mitose (igual a K10_MAX_GROUP)
const K10_TRANSFER_SIZE = 180; // 10% dos usuários mais recentes → Filho
const K10_TUTOR_TARGET = 1700; // Filho considerado adulto
const K10_ALERT_LOW = 1600; // alerta amarelo
const K10_CRITICAL_LOW = 1400; // alerta vermelho, compensação ativa
const K10_MERGE_THRESHOLD = 1700; // fusão se Pai+Filho ≤ este valor
const K10_MERGE_DEBOUNCE_MS = 300000; // 5 min estável antes de fundir
const K10_COMPENSATE_DELTA = 100; // usuários transferidos por ciclo

All constants are defined on the client (K10_...) and must be mirrored on the server for decision logic.

✂️

1. Mitosis — group-split

When: A group reaches K10_SPLIT_THRESHOLD (1800) members.

Server action:

  • Select the 180 most recent users (lowest session time).
  • Create a new child group with a fresh 4‑character GID.
  • Send group-split to all clients in both parent and child groups.
{
  "type": "group-split",
  "msgId": "split_<uid>",
  "parentGid": "ABCD",
  "childGid": "EFGH",
  "parentSize": 1620,
  "childSize": 181,
  "iAmTransferred": true // true for moved users, false for others
}

Client behaviour: Updates directoryGlobalRef with new sizes. If iAmTransferred === true, updates myGroupIdRef and localStorage. Peer ID never changes.

📌
After split: parent = 1620 users, child = 181 users (180 transferred + 1 new entrant).
🎓

2. Tutelage — group-tutor-status

When: A child group is created (after mitosis) and until it reaches K10_TUTOR_TARGET (1700).

Server action: Broadcasts tutelage state periodically and when child size changes significantly.

{
  "type": "group-tutor-status",
  "msgId": "tutor_<uid>",
  "childGid": "EFGH",
  "parentGid": "ABCD",
  "childSize": 450,
  "active": true
}

Weighted routing table (server must implement when directing new users):

Child < 50095% of new users → child 500–99980% → child 1000–149960% → child 1500–169930% → child ≥ 17000% (tutelage ends, send active: false)

Clients store the tutelage state in groupTutorStateRef for routing hints when acting as relays.

⚠️

3. Alerts — group-alert

When: Group size falls below thresholds.

Yellow alert (1600)Group stops accepting new users. Red alert (1400)Compensation is triggered.
{
  "type": "group-alert",
  "gid": "ABCD",
  "size": 1380,
  "level": "red",
  "siblingGid": "EFGH"
}

Clients update the directory and show a system message if the user belongs to the affected group.

⚖️

4. Compensation — group-compensate

When: A group stays in red alert (size < 1400) and its sibling group is larger.

Server action: Transfers K10_COMPENSATE_DELTA (100) users from the larger group to the smaller.

{
  "type": "group-compensate",
  "donorGid": "EFGH",
  "receiverGid": "ABCD",
  "donorNewSize": 1650,
  "receiverNewSize": 1650,
  "iAmTransferred": false
}

Invariant: After compensation, both groups have approximately (total / 2) users. The difference becomes < K10_COMPENSATE_DELTA.

🔄

5. Fusion — group-merge

Condition: parentSize + childSize ≤ K10_MERGE_THRESHOLD (1700) for at least K10_MERGE_DEBOUNCE_MS (5 minutes) without oscillation.

Server action: Merge the smaller group into the larger one.

{
  "type": "group-merge",
  "msgId": "merge_<uid>",
  "survivorGid": "ABCD",
  "dissolvedGid": "EFGH",
  "survivorNewSize": 1200
}

Client behaviour: Merges reservados lists, removes the dissolved group from directory, updates myGroupIdRef for migrated users. Peer ID unchanged.

⏱️
Debounce prevents “frenetic merging” when sizes oscillate near the threshold.
🛟

6. Orphan Rescue — group-orphan-rescue

When: Server detects that a child group’s server has gone offline (no heartbeat for 30 seconds).

{
  "type": "group-orphan-rescue",
  "rescuerGid": "ABCD",
  "orphanGid": "EFGH",
  "rescuerNewSize": 1800
}

All users from the orphan group are reabsorbed into the rescuer group. The orphan GID is removed from the global directory.

7. Size Report & Debounce — group-size-report

Purpose: Periodically synchronise group sizes from server to clients and evaluate merge conditions.

{
  "type": "group-size-report",
  "groups": [
    { "gid": "ABCD", "size": 650 },
    { "gid": "EFGH", "size": 800 }
  ]
}

Clients update their local directory and start/stop the 5‑minute merge debounce timer. If the sum of two sibling groups stays ≤ 1700 for the entire debounce period, the client logs a suggestion; the server ultimately decides to send group-merge.

System Architecture & P2P Physics

For engineers and curious minds, this section details the underlying mechanisms of the Hydra Network. It explains how the chat avoids infinite loops, how islands of users merge or split, and how servers handle overwhelming scale.

01

Organic Propagation: The Reciprocal Flow

Messaging in the General Web operates through a bidirectional chain: Parent ↔ Child ↔ Grandchild. Every WebRTC channel is perfectly reciprocal. If the Parent shouts a message, it passes down the line. If the Grandchild replies, it travels back up. However, in a mesh, a Grandchild might also be connected back to the Parent, creating a severe risk of an infinite broadcast storm (the "Echo").

Hydra solves this using two absolute shields:

💾 The "I've Seen It" LogEvery device runs a high-speed LRU Hash Cache that memorizes exactly the last 10,000 message IDs. If a message circulates around the globe and comes back to you, your cache detects the duplicate and silently drops it, killing the echo instantly. ⏱️ The Breath (TTL)Messages are born with a Time-To-Live (TTL = 15). Every time it hops from user to user, the TTL decreases by 1. At 0, the message dies of exhaustion. Heavy protocol messages (like topological sweeps) use a smaller TTL (4 or 5) to save bandwidth.
02

The Bouncer: Auto-Hydra at 200 Users

A typical server completely collapses when too many users connect. Chat K10 avoids this by transforming the Server's role when it reaches its physical limit (150-200 concurrent WebSockets).

🚪 The Chat Door ClosesThe server stops acting as a central relay. It refuses to read or re-transmit heavy chat messages, audio, or files for the external network. 📡 Becoming a Bouncer (Tracker)Users pushed out into the decentralized Mesh simply send tiny radar pings (p2p-heartbeat) to the server every few seconds. The server's only job is to note down: "Okay, User X is currently alive on the street." 🔗 PEX Injection (Routing)When New User 201 knocks on the server's door, the server answers: "The VIP room is full, but the party continues outside. Connect directly to these 10 people I just saw on my radar." The server hands over a Peer Exchange (PEX) list and hangs up. The new user uses those IDs to join the infinite Mesh.
03

Friendly Servers (Federated Trees)

To break a single server's limits without forcing users onto the mesh, Server Owners can federate by inserting another server's -CENTRAL ID.

🌐 The Express TubeAn invisible, high-speed WebRTC channel links Server A and B. When User X sends a message on Server A, it distributes to Server A's crowd and travels the tube to Server B, which relays it to its crowd. Thousands of users behave as if they share one room. 🛡️ Crash Resilience (Fail-over)If the owner of Server B loses power, the global room doesn't die. The link simply breaks. Server A and Server C continue routing their local hubs peacefully. It is true decentralization across administrators.
04

Healing the Network: Split & Merge

The mesh constantly mutates based on internet connectivity. Two algorithms prevent the P2P tree from rotting or inflating infinitely.

🔪 Fission (Group Split)If an internet cable cuts a continent in half, nodes notice that heartbeats from the other side have been missing for exactly 90 seconds (90,000ms). The surviving nodes panic-evaluate: they alphabetically sort all their IPs and elect the top 10 strongest nodes (requiring ≥ 20 connections and desktop-class hardware). These new leaders broadcast a group-split packet, officially severing ties and cleanly resetting the network's state.
🤝 Fusion (Group Merge)If two isolated islands (Group A and Group B) suddenly meet, they broadcast a group-merge. To prevent ghost multiplication (e.g., A hears the merge 5 times and inflates the user counter infinitely), the engine employs a strict rule: Math.max(surviving, surviving+absorbed, absorbed). Additionally, the new mega-group is capped at 10 Reserved Leaders (slice(0, 10)). This ensures immediate geographical healing without blowing up the browser's RAM routing tables.

Security & Abuse Prevention

Chat K10 includes multiple protection layers against misuse, even if someone modifies the client code to attack the network.

Automatic Anti-Spam Measures

⏱️
Message rate limitingEach user must wait between messages based on network size: wait = max(1s, ⌊networkSize/1000⌋ × 1s) — minimum always 1 second; grows with the crowd (e.g. 2,000 users → 2s wait).
🚫
Three-strikes banAfter 3 spam violations, the offending peer is locally banned and the connection is closed.

Anti-Loop & TTL System

Every message carries a unique ID and a TTL (Time-To-Live) counter (default: 15). Each retransmission decrements TTL by 1. When TTL reaches 0, the message is discarded. Servers and clients maintain a cache of up to 10,000 recently seen message IDs to prevent duplicate processing.

FAQ & Troubleshooting

"I see a white screen for a few seconds when opening" —
Normal on first load — the browser is compiling React/JSX with Babel. Wait 3–7 seconds; a loading spinner appears. For faster startup, host the HTML file on a local web server instead of opening directly from disk.
"My friend cannot connect to me" —
Make sure both of you are online and have allowed microphone/camera permissions if needed. Try using a server (connect to a -CENTRAL server) — it helps with strict firewalls and symmetric NAT. If behind a very restrictive network, use General Web mode (deselect all contacts). Your message will find a path through the mesh.
"Encryption doesn't work" —
Both sides must exchange secrets. Just sending your secret is not enough — the other person must also click the 🔑 button and send their secret to you. Check the indicator next to the contact's name: 🔒 means fully active E2EE.
"The server is full / I got a migration message" —
The server reached its 150-user Auto-Hydra threshold. You were automatically moved to the General Web — this is normal and good; the network is scaling. You can keep chatting normally without any interruption.
"Quiz Bot questions appear in the wrong language" —
Change your language in the header dropdown. The next questions will be auto-translated via Google Translate. On very slow connections you might briefly see the original language before translation completes.
"What happens if I stop the Quiz Bot?" —
If you click "Stop Bot", the bot automatically transfers to the connected server (if any). The server continues sending questions without interruption from exactly where you left off. If no server is connected, the bot stops completely.
"My video call is laggy" —
Video calls depend on your upload speed. Switch to voice-only for a much lighter load. Use direct P2P mode (not through a server relay) for best performance. Quality controls are planned for a future version.
"I can't send files larger than 5 MB" —
5 MB is the limit for direct WebRTC file transfer. For larger files, use the Torrent Manager in the Tools menu — it supports files up to 500 MB via WebTorrent (only the magnet link travels through the chat).
"What is the difference between a Peer ID and an Invite Link?" —
Peer ID: A 9-character code (e.g., A3BX7KQ2P or MyServer-CENTRAL) that identifies you on the network. Share it manually by copying and pasting. Invite Link: A full URL generated only by the client. When someone clicks it, the chat opens and automatically connects to all listed peer IDs — convenient for inviting multiple people at once.
"How does the General Web have no user limit?" —
There is no central server. Each user connects to up to 15 others (50 in SuperNode mode). Messages hop from user to user up to 15 times (TTL). The network grows organically — more users make it stronger, not weaker. The 200-connection server limit only applies when you choose to use a relay server. The General Web is truly limitless.
