Introduction

Chat K10 V69 is a fully self-contained, decentralized communication platform. There is no separate server application. Everything — chat, relay hub, Quiz Bot, media tools, Monitor, Benchmark — lives inside a single ChatDesktop.HTML file. Open it in any modern browser and you are immediately part of the network.

Unlike traditional chat apps (WhatsApp, Telegram, Discord), your messages never pass through a company database. You talk directly to other people (Peer-to-Peer) or through relay hubs that emerge automatically from within the network itself — no dedicated server machine required.

Key Principles

📄
Single HTML file — zero installationChat K10 is one self-contained file. No backend, no npm, no account. Open and chat.
🔒
End-to-end encryption (AES-256-GCM)Only the recipient can read your messages — not even a relay hub operator.
🚫
No central databaseNobody stores your conversations. Data stays between peers only.
👑
Built-in relay hub (automatic election)One Chat K10 instance per network silently becomes the K10‑CENTRAL discovery hub. No separate server file needed.
🔗
Share links, not heavy dataYouTube, radio, and most media are shared via URLs. Each user streams from the original source.
⚠️
CRITICAL: The "Private" tab alone does NOT guarantee privacy.
When you send a message in the "Private" tab without encryption, the message travels in plain text and may be received and read by other users connected to the same mesh.

✅ The only way to ensure that only you and the intended recipient can read the content is to activate bilateral E2EE (🔑) as described in the Encryption section below.

Four Network Topologies

The routing architecture of Chat K10 operates across four distinct topological flows. All four modes are available from within the same ChatDesktop.HTML file — no additional software required.

TOPOLOGY 01
User ↔ User
Direct P2P channel. No relay, zero intermediary latency.
TOPOLOGY 02
User ↔ Hub ↔ User
Star topology. A K10‑CENTRAL relay hub rebroadcasts messages to a group.
TOPOLOGY 03
Hub ↔ Federated Hubs ↔ Users
Tree topology. Multiple relay hubs link together; multiplies capacity immensely.
TOPOLOGY 04
General Mode (Hydra Mesh)
Controlled flooding. Everyone relays to everyone — no hub required.
01

User ↔ User (Direct P2P)

Two browsers establish a direct WebRTC connection. No relay in the middle. The message travels directly from sender to recipient over the shortest possible network path.

✅ Best forPrivate one-on-one conversations, voice/video calls, file transfers.
02

User ↔ Relay Hub ↔ User (Central Relay)

Everyone connects to one K10‑CENTRAL hub — a Chat K10 instance that was automatically elected as the group relay. The hub rebroadcasts messages to all connected users. No separate server application is needed; the hub role is played by a regular Chat K10 client that wins the shadow election.

✅ Best forStable group chats, users behind strict firewalls or symmetric NATs.
03

Federated Hubs (Tree Topology)

A "Tree" topology. Hubs link together by sharing each other's K10‑CENTRAL ID. Messages propagate across all federated hubs automatically.

✅ Best forMassive audiences crossing the 200-user limit of a single hub.
04

General Mode (Hydra Mesh / Flooding)

No hub required. Messages hop from user to user (up to 15 hops TTL). Every node uses an LRU cache of message IDs to drop duplicates.

✅ Best forCensorship‑resistant broadcasting, automatic overflow when a hub is full.
🌐
Cross‑gateway peer sampling (V58+): Each gateway periodically probes other gateways and exchanges samples of their real clients. When a newcomer joins a gateway with fewer than 5 local peers, those external peer IDs are included in the peer-list. The discovery interval is adaptive: first 3 cycles every 5 seconds, then every 30 seconds.
⚠️
In General Mode, every message is broadcast to the entire mesh. If you need private conversation with two people only, do not use General Mode — select the contact in the Private tab and activate E2EE (🔑).

Built-in Relay Hub

Chat K10 V69 does not require any separate server application. The relay hub is an emergent role that one Chat K10 instance assumes automatically via a background election process (K10CentralShadow). Any user running Chat K10 may silently become the hub — the network self-organizes.

✅
No extra files needed. The hub role, all discovery logic, router mode, federation, and auto-hydra scaling are all built into ChatDesktop.HTML. There is no server.html or external service to run.
👑
Automatic K10‑CENTRAL Election (Shadow Election)

The module K10CentralShadow runs silently in every Chat K10 instance. The peer with the lowest peer ID among all known nodes automatically becomes the elected central hub. It registers the ID K10‑CENTRAL and answers central-discovery-request messages with the list of active gateways. If the elected peer disconnects, the next peer in order takes over immediately — zero user intervention, completely silent.

🚏
Router Mode (Zero‑State Operation)

When active, the elected hub never keeps persistent WebRTC connections. It assigns a group ID to each newcomer via peer-list and disconnects them after 3 seconds. The hub functions purely as a directory. This allows the hub role to handle far more users because it never holds WebRTC state. This mode is activated automatically or can be toggled from the hub interface within Chat K10.

🐉
Auto-Hydra Overflow — Self-Scaling

When the hub reaches 150 connected users, it automatically switches to Hydra mode: it sends a list of known peers to everyone, then disconnects them. All users migrate to the General Mesh — the chat never stops. This is how the network scales infinitely without crashing the hub.

🤝
Hub Federation (Tree Topology)

A hub can add another hub's -CENTRAL ID as a contact. Once connected, the two hubs form a federated tree. When User A sends a message: Hub A broadcasts to its users → forwards to every federated hub → each hub broadcasts to its users. The same TTL and anti‑loop cache applies. Each hub handles up to 200 users — federation allows thousands across multiple hubs running inside regular Chat K10 instances.

📺
YouTube Live Chat Broadcasting

Any Chat K10 instance (including a hub) can mirror a YouTube Live chat to all connected users. They see a second tab — Chat YouTube — with live comments. Start via Tools → Start YouTube Chat and paste the YouTube Live URL.

📊
Hub Statistics (Real-Time)

The hub interface inside Chat K10 shows a live dashboard: messages received / distributed · active connections · estimated Hydra Web size (P2P node count) · full audit log with all connection events.

Audit Log & Network Health

The Audit Log (📜 Audit Log) is the "Pulse" of the Chat K10 network. It ensures complete transparency by logging real-time connectivity events, errors, and automated maintenance actions across the entire decentralized structure.

🔍 Automated Monitoring

Every Chat K10 instance maintains its own detailed Audit Log to detect "Ghost Connections" and verify synchronization. Every entry includes a precision timestamp and is color-coded by severity category.

✅ OKSuccessful handshakes, peer connections established.ℹ️ INFOHydra network structural changes (group split/merge) or auto-reconnection logs.⚠️ WARNGhost connection detected by GC, peer disconnected.❌ ERRORPeer ID already in use, remote peer not found.
GC

The "Ghost Connection" Garbage Collector

Chat K10 runs an active Garbage Collector (GC) every 5 seconds to ensure network stability. It monitors the connectionState of every remote peer; if a peer is failed, closed, or disconnected, the GC force-closes the socket and purges UI references.

🔒
V69 — Quiz Bot Lock System (4 rules enforced):

LOCK-1 — Exclusive owner: Only the peer who activated the Quiz Bot can stop it. The stop signal is compared against the original owner's peer ID, not the receiver's.

LOCK-2 — Non-owners never see the Stop button: Other users receive a static locked panel (a div), not a button element — so the stop action is completely absent from their DOM.

LOCK-3 — Auto-stop on owner disconnect: When the owner disconnects, a 15-second timer starts. If the owner does not reconnect within that window, the quiz stops automatically and a quiz-bot-global-toggle{active:false} is broadcast to all peers.

LOCK-4 — Late-joiners receive the lock state: When a new peer connects after the quiz is already active, the handshake includes the current quiz state so they immediately see the locked panel.
⚠️
No server handoff: Because there is no external server, the Quiz Bot does not hand off to any other application when stopped. When the owner clicks "Stop Bot" or disconnects (and does not return within 15 s), the quiz ends completely for all users.

Encryption (E2EE) — The Only Real Privacy

🚨
READ THIS FIRST: The "Private" tab only organises the interface — it does NOT encrypt your messages. Without encryption, your messages travel in plain text and can be read by other users or relay hub operators if routing goes wrong.

You must activate bilateral E2EE (🔑) to ensure that only the intended recipient can read the content. With encryption active (🔒 icon next to the contact), even if a message is misrouted, nobody else can decrypt it.

Step-by-Step to Activate Encryption

1
Click the 🔑 button in the message input bar
A modal window opens listing your online contacts.
2
Select the contact who is online and connected
Only currently online contacts appear as selectable.
3
Click "Send Secret Now"
Your browser generates a unique cryptographic secret and sends it directly via P2P — the relay hub never sees it.
4
The other person must do the same for you
⚠️ Critical: encryption is bidirectional. They must also click the button and send their secret to you. Sending only yours is not enough.
5
Look for the lock icon — you're fully encrypted
Once both sides have exchanged secrets, a 🔒 appears next to the contact's name. All subsequent messages are E2EE.

Encryption Indicators

🔒
Full E2EE ActiveBoth sides exchanged secrets. All messages encrypted in both directions.
📤
Sending EncryptedYou sent your secret, but the other side hasn't replied yet. Your outbound messages are encrypted; inbound are not.
📥
Receiving EncryptedYou can read their encrypted messages, but you haven't sent your secret yet.
🔐
Group EncryptionGroup E2EE active on a relay hub channel. Messages pass through fully encrypted.
✅
With E2EE active (🔒), your conversation becomes truly private. Even if the network misroutes a packet, only you and the recipient hold the keys to decrypt it. This is the only way to prevent message "leaks" to other users.

Group Encryption on Relay Hubs

If connected to a -CENTRAL hub, you can activate group encryption. Prerequisite: you must have exchanged individual secrets with every participant first. Click the encryption button next to the hub in the conversations list. A group secret is generated and sent to all contacts who already have E2EE with you. From then on, all messages through that hub are encrypted — the hub sees only ciphertext. Users without the group secret see blank messages.

⚠️
New users joining later do not automatically receive the group secret. An existing participant must manually share it with them out-of-band.

Groups in V69 — Logical Rooms & Binary Protocol

Chat K10 organises the Hydra mesh into logical groups (rooms). Each group has a Logical Group ID (volatile) and each user retains a permanent Peer ID stored in localStorage.

⚠️
Public PeerJS limitations: K10_MAX_GROUP is 50. All homeostatic constants have been proportionally scaled. The fixed suffix list contains 50 positions (AA … up to the 50th combination).
01

Fixed Peer ID vs. Logical Group ID

🔐 Peer ID (permanent)Random 9-character string stored in localStorage. It never changes, ensuring your private conversations, contacts and files remain attached to you.🧩 Logical ID (volatile)Built as K10 + GID (4 chars) + suffix (2 chars). Changes when you move between rooms or when the group reorganises itself.
02

The Fixed Suffix List — No More Name Spam

Every copy of Chat K10 contains an identical, hard-coded list of 50 suffixes (AA … up to the 50th combination). Because all clients share the same list, the hub never sends the full set of names. Instead, it sends only the total number of people in the group (count). This reduces group-update bandwidth by up to 83%.

03

Binary Protocol — 7‑Byte Messages

All group join/leave events are transmitted as ultra-lightweight binary packets (7 bytes). No JSON, no human-readable names — just raw bytes. This includes JOIN_UPDATE (when someone joins) and PEX_UPDATE / SWAP-ON-LEAVE (when someone leaves).

🌿

V27 Homeostatic Protocol (Scaled for 50 users)

Chat K10 V27 extends the group system with a hub-driven homeostasis layer. The elected hub automatically monitors group sizes and applies corrective actions to keep the network balanced. All constants are scaled for 50 users.

K10_MAX_GROUP = 50 // maximum users per group
K10_SPLIT_THRESHOLD = 50 // triggers mitosis
K10_TUTOR_TARGET = 47 // child group considered adult
K10_MERGE_THRESHOLD = 47 // fusion if parent+child ≤ this
K10_COMPENSATE_DELTA = 3 // users transferred per cycle

Handlers implemented: group-split, group-tutor-status, group-alert, group-compensate, group-merge, group-orphan-rescue. Peer ID never changes; only myGroupIdRef is updated.

⏱️
Debounce (5 minutes) prevents "frenetic merging" when sizes oscillate near the threshold.
🧠

System Architecture & P2P Physics

Messaging in the General Web operates through a bidirectional chain: Parent ↔ Child ↔ Grandchild. To prevent infinite broadcast storms, every message has a TTL (Time-To-Live) (max 15 hops) and every node maintains an LRU cache of message IDs to drop duplicates.

01

Organic Propagation: The Reciprocal Flow

The Hydra mesh ensures no echo loops via the "I've Seen It" log (LRU cache) and the TTL counter. Every message dies after 15 hops.

02

Bootstrap Optimisation (V68+)

When Chat K10 starts, it first tries to connect to K10-CENTRAL (the currently elected hub). If successful, it receives a list of active gateways (K10-GATE-XXXX) that are known to be online. It then probes those gateways in parallel batches of 5 and accepts the first that returns a peer-list with real users. If K10-CENTRAL does not respond, it falls back to scanning all gateways sequentially. This reduces join time from 13–16 seconds to ~2–4 seconds.

03

Federated Hub Trees

Hubs can federate by inserting another hub's -CENTRAL ID. An invisible WebRTC channel links Hub A and Hub B, allowing thousands of users to behave as if they share one room.

FAQ & Troubleshooting

"I'm in the Private tab, but other users receive my messages!" —
Cause: You haven't activated E2EE encryption. Without encryption (🔒), messages travel in plain text and network routing bugs can cause them to be delivered to unintended recipients — especially if you are connected to a relay hub or the Hydra mesh.

Solution: Activate bilateral encryption (🔑) with your intended contact. Once both sides have exchanged secrets (🔒 appears), the messages are encrypted end-to-end. Even if a packet is misrouted, no one else can decrypt it.
"Encryption doesn't work" —
Both sides must exchange secrets. Just sending your secret is not enough — the other person must also click the 🔑 button and send their secret to you. Check the indicator: 🔒 means fully active E2EE.
"The hub is full / I got a migration message" —
The elected hub reached its 150-user Auto-Hydra threshold. You were automatically moved to the General Web — this is normal and good; the network is scaling.
"Connection takes a long time to start" —
The client uses an optimised bootstrap (V68+): it first asks K10-CENTRAL (the current elected hub) for a list of active gateways, then probes them in parallel batches of 5. This typically finishes in 2–4 seconds. If you still experience long delays, the discovery hub may be missing — the client falls back to a full gateway scan.
"Quiz Bot questions appear in the wrong language" —
Change your language in the header dropdown. The next questions will be auto-translated via Google Translate.
"What happens if I stop the Quiz Bot?" —
Only the user who started the Quiz Bot (the owner) can stop it. When the owner clicks "Stop Bot", the quiz ends completely for all users — there is no external server to hand off to. If the owner disconnects, a 15-second grace period begins; if they don't reconnect, the quiz stops automatically and all users are notified.
"My video call is laggy" —
Video calls depend on your upload speed. Switch to voice-only for a much lighter load. Use direct P2P mode for best performance.
"I can't send files larger than 5 MB" —
For larger files, use the Torrent Manager in the Tools menu — it supports files up to 500 MB via WebTorrent (only the magnet link travels through the chat).
"What is the difference between a Peer ID and an Invite Link?" —
Peer ID: A 9-character code that identifies you. Invite Link: A full URL generated by any client that auto-connects to multiple peers.
"How does the General Web have no user limit?" —
There is no central server. Each user connects to up to 15 others (50 in SuperNode mode). Messages hop up to 15 times (TTL). The network grows organically — more users make it stronger, not weaker.
"Do I need to run a separate server application?" —
No. Chat K10 V69 is fully self-contained. The relay hub role is assumed automatically by one of the connected Chat K10 instances (shadow election). You only need the single ChatDesktop.HTML file.
